# 行业痛点分析

本 Skill 是盒子原创行业研究 Skill 组合中负责行业痛点分析的专项 Skill，识别“谁在什么情境下，因为完成什么任务或经过什么节点，反复、持续，或在关键时点承担什么现实损失，以及现有办法为什么仍不够”。

不要把抱怨、需求、风险、供应商卖点或行业难题清单直接命名为痛点。

需要使用分析表时，读取 [`references/行业痛点分析工作表.md`](references/行业痛点分析工作表.md)。

## 1. 定位与边界

本 Skill 可独立使用，也可读取案例、结构、经营、竞争或其他分析结果。它以“承担者和现实损失”为分析单位，直接整理与痛点有关的材料，不扩成完整产业、经营或案例专题；驱动可造成痛点，痛点也可成为行业约束，但二者不得在同一评分中相互抵消。

不承担完整信源评级、无关案例库重编码、市场规模、产品设计、战略或投资结论；负责本专项分析和 Markdown 交付，不扩成完整行业或企业总报告。

## 2. 启动与工作流程

- **由 `hehe-industry-researcher` 调用：** 收到任务卡和材料索引后直接读取材料并执行，不重新启动路由。
- **用户直接调用本 Skill：** 本 Skill 单独启动，在对话中确认对象、研究范围、地域、时间、用户口径要求及已有材料，再决定是否搜索。

开始执行前读取 [专项工作流程](references/专项工作流程.md)，按对应路径接任务、搜索、审核、分析、自审和交付。
交付时读取 [行业痛点分析交付模板](references/行业痛点分析交付模板.md)，按模板完成本专项成果；用户明确不落文件时，在对话中交付。

**完整交付原则。** 用户要求完整、深度或系统研究，或本专项作为 `hehe-industry-researcher` 完整研究中的适用模块时，必须先形成独立完整专项报告，不得因后续还会汇总而只返回摘要、任务卡或几条结论。只有用户明确要求局部／简版，或资料只能支持有限披露时才切换输出模式，并在报告中标明；完整度按交付模板的分析单元和正文目标体量检查，交付前实际计数。

## 3. 核心分析方法

以下五步构成一条完整判断链。问题较小时可以简写，但不能把候选表达直接跳写成行业痛点。

### 1. 明确范围、承担者与任务

每个候选使用：

```text
承担者 × 任务/流程/产业节点 × 情境 × 时间窗口
```

承担者可为 C 端用户、使用者、采购者、决策者、付款方、实施者、企业客户、供应商、服务商、渠道、劳动者、监管执行方或其他参与者。B/G 端按实际情况拆开需求发起、付款、审批、采购、使用、实施、验收和责任承担角色。不同承担者、任务、节点或时期不得合成一个模糊的“行业痛点”。

### 2. 整理候选并选用合适的分析方式

先区分候选是什么：

| 候选类型 | 如何处理 |
|---|---|
| 需求 | 记录希望完成的任务或结果；只有未满足并造成现实损失时才升级为痛点候选 |
| 抱怨/情绪/反馈 | 作为表达线索；核对行为、资源投入、结果或持续机制，不自动外推 |
| 流程摩擦 | 判断是否反复增加时间、成本、错误、协调或放弃，不因一次不便就上升为行业痛点 |
| 产业瓶颈 | 核对节点受阻的材料，识别承担者、损失和绕行成本 |
| 经营约束 | 核对采购、合同、成本、回款等经营材料，区分主体特有问题与行业共性 |
| 风险 | 尚未发生时标为风险暴露；已经形成保险、合规、准备、责任或机会成本等当前负担时，再分析现实痛点 |
| 产品卖点/节省承诺 | 只作为待核主张，不能反向证明痛点存在或可解决 |
| 行业痛点 | 明确承担者在明确任务或节点上反复、持续，或在关键时点承受可观察损失，且当前替代仍存在明显缺陷 |

再根据材料选择分析方式：

- 材料少、差异大或没有分母：做定性辨析；
- 部分字段可追溯且单位一致：以定性为主，对这些字段做有限计数；
- 分析单位、可比字段、分母及材料形成过程都能说明：做样本内综合。

Agent 默认选择并说明理由；只有选择会明显改变工作量、统计范围或结论强度时，才请用户确认。数量不自动决定分析方式。需要计数时记录分类规则、去重和分母；分类不稳时保留定性观察。

整理候选时，至少保留承担者、任务或节点、情境与时期、原始表现、可能的损失、现有替代、来源、反例和缺口。原始表达、已有事实、研究者推断和本 Skill 结论分开；没有损失证据的项目仍可作为需求、抱怨、风险或待核候选，但不升级为痛点。

### 3. 核查现实损失及其未被解决的原因

先分清三件事：表面症状是看见了什么，形成原因是为什么发生，现实损失是给谁带来了什么后果。对核心候选整理：

```text
触发/条件 → 任务或节点受阻 → 立即负担 → 应对行为 → 下游结果 → 持续或缓解机制
```

现实损失可以包括时间与等待，直接成本、预算占用和现金压力，收入、订单、转化、产能或机会损失，错误、返工、质量、交付或结果偏差，合规、安全、信誉、法律或责任负担，协调、认知、组织和情绪负担，以及放弃、不行动、流失、非消费或替代迁移。

证据可以表现为主观表达、实际行为、资源投入、交易或预算、经营结果及跨角色影响。这些不是必须逐级通过的固定阶梯；只需说明已经观察到什么、尚缺什么。

同时核对现有产品、服务、人工、自建、外包、流程变通、不行动或退出：它解决了哪一段，留下了什么，是否把成本、风险或责任转给另一角色，以及采用所需的预算、能力、集成、迁移、学习、信任、审批或合规条件。替代未被采用或未能持续，可能是痛点不强、方案不佳、预算不足、责任错位或资料不足，不能直接归因。“存在解决方案”不等于痛点消失，“缺少新技术”也不等于存在商业机会。

### 4. 判断发生范围、持续方式与当前重要性

分别判断：

- 是单一主体特例、特定分群或特定节点问题，还是在多个独立主体或角色中重复出现；
- 是否集中在某地域、时期、规模、技术路线、客户类型、采购制度或业务模式；
- 是一次事件、周期性问题、过渡摩擦、结构性持续负担，还是低频但在关键时点造成重大后果；
- 主动发声、极端案例、供应商宣传和公开材料选择机制是否放大可见度；
- 满意者、无需求者、成功绕行者、沉默主体和反例是否被遗漏。

没有分母时不输出发生率、普遍性或行业比例。多个案例出现只支持“当前材料中的重复观察”，不自动证明行业共性。

不使用跨行业固定权重或统一总分。结合当前问题判断损失是否真实且足以改变行为或经营结果、承担者和覆盖范围是否清楚、替代是否昂贵或低效、损失能否缓解、证据是否独立，以及哪些条件会强化、减弱或消除问题。可使用“关键痛点候选、重要但分群化、局部或阶段性负担、弱线索、非痛点、暂不判断”等结论；不可比较时分组呈现，不强行排名。当前重要性不能直接证明商业可解性、付费意愿、市场规模或投资价值。

### 5. 形成结论、限制与后续观察

每条核心结论至少说明：谁在什么任务或节点、什么情境和时期承担了什么损失；问题如何形成；现有替代为何仍不够；当前判断适用于哪些对象；哪些反例、缺口或变化会削弱结论。

总体判断使用 `成立｜条件成立｜不成立｜暂不判断`。`不成立`表示现有证据支持排除该痛点命题，`暂不判断`表示关键证据不足。需要补证时，把会影响核心判断的缺口转成任务；任务允许且有可用搜索能力时，在本次分析中补充，无法解决时降低结论强度并保留缺口：

```text
痛点候选｜缺失的承担者/情境/损失/替代字段｜对象/地域/期间｜需要的原文或现实结果｜用于区分什么解释｜可接受替代｜补充后更新哪一部分
```

## 4. 验收

- [ ] 每个核心候选均有明确承担者、任务/节点、情境和时期。
- [ ] 需求、抱怨、摩擦、瓶颈、经营约束、风险、卖点和痛点没有混写。
- [ ] 现实损失、行为或结果依据可追溯；没有用供应商承诺反证痛点。
- [ ] 原始表达、已有事实、推断和痛点结论分列。
- [ ] 现有替代、绕行、不行动及其新增负担已经核对。
- [ ] 主体特例、分群重复和行业共性没有相互冒充。
- [ ] 少量材料允许定性观察；任何计数都有单位、分母和样本边界。
- [ ] 分析方式与材料条件匹配；需要人工讨论时已说明选择及风险。
- [ ] 材料整理与编码服务于本题痛点判断，没有扩成无关的完整专题。
- [ ] 优先级是条件性判断，没有固定权重、伪精确分数或商业机会跳跃。
- [ ] 允许且必要的关键补证已经执行；未解决缺口、新材料状态和判断边界已经标明。
