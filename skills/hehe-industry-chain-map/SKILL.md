# 产业链结构分析

本 Skill 是盒子原创行业研究 Skill 组合中负责产业链分析的专项 Skill，回答“行业必须经过哪些环节、哪些角色彼此交易和交付、各层有哪些代表企业、订单资金数据责任怎样流动、瓶颈与价值如何迁移”。

## 定位

本 Skill 回答七个问题：

1. 一个产品或服务从需求产生到最终交付，必须经过哪些功能环节；
2. 每个环节由哪些角色完成，他们分别向谁采购、向谁销售或交付；
3. 哪些真实企业或机构是各层的代表性参与者，哪些核心层值得重点关注；
4. 订单、资金、数据和责任分别经过谁，四条流是否一致；
5. 哪个环节的供给最难扩张、最难绕开，为什么；
6. 谁承担成本、库存、交付或合规责任，谁取得议价权与价值；
7. 替代、扩产、技术变化或纵向整合会不会让瓶颈迁移。

本 Skill 交付产业结构、角色关系、分层企业图谱和可编辑的产业链图；正常文件交付同时附离线 HTML 图形预览，无法实际渲染时按交付模板降级，不以 Logo 墙或企业排名代替分析。

## 启动与工作流程

- **由 `hehe-industry-researcher` 调用：** 收到任务卡和材料索引后直接读取材料并执行，不重新启动路由。
- **用户直接调用本 Skill：** 本 Skill 单独启动，在对话中确认对象、研究范围、地域、时间、用户口径要求及已有材料，再决定是否搜索。

开始执行前读取 [专项工作流程](references/专项工作流程.md)，按对应路径接任务、搜索、审核、分析、自审和交付。
交付时读取 [产业链分析交付模板](references/产业链分析交付模板.md)，按模板完成本专项成果；用户明确不落文件时，在对话中交付。

**完整交付原则。** 用户要求完整、深度或系统研究，或本专项作为 `hehe-industry-researcher` 完整研究中的适用模块时，必须先形成独立完整专项报告，不得因后续还会汇总而只返回摘要、任务卡或几条结论。只有用户明确要求局部／简版，或资料只能支持有限披露时才切换输出模式，并在报告中标明；完整度按交付模板的分析单元和正文目标体量检查，交付前实际计数。
绘图时读取 [产业链图绘制规范](references/产业链图绘制规范.md)，保留 Mermaid 图源，并按角色层级、关系与图例完成二次美化。

## 分析流程

### 1. 明确分析范围和产业链要完成的任务

先用一句话说明这条产业链需要完成什么，例如“把某类原料转化为通过认证并被终端客户使用的产品”或“把用户需求转化为可持续交付的服务”。

同时写清：

- 包含与排除的产品、服务和辅助环节；
- 起点、终点以及是否包含售后、回收和基础设施；
- 最终付款者、决策者、使用者是否为同一主体；
- 分析的是全球结构、本地供给还是跨境链条；
- 基准时点和需要解释的结构变化。

不得把“常见四层模板”直接当作当前行业结构。

同时建立分析配置卡：

`决策用途｜分析粒度｜节点展开规则｜结构拓扑｜主链/支链/反馈回路｜包含与省略理由｜后续用途`

- **全景**用于看完整系统与主要接口，**中景**用于展开关键链段，**近景**用于拆解单一节点或卡点；也可按课题自定义粒度。
- 粒度不对应固定层数或固定公司数量；同一课题可先全景定位，再对关键链段形成中景或近景子图。
- 结构拓扑可为主链、并行链、双边网络、闭环或混合结构。政策、标准、基础设施等只有在承担必要功能或控制接口时才进入结构，不自动增加固定层级。

分析时分清三层：**功能链**说明行业必须完成什么，**角色链**说明谁与谁发生上下游关系，**企业图谱**说明哪些真实主体占据这些角色。三者相互校验，但不能互相替代。

### 2. 先拆必要功能，建立功能链和结构拓扑

按照“缺少这个功能，最终交付是否还能完成”识别必要节点。一个节点至少记录：

`节点/功能｜主要输入｜主要输出｜上游接口｜下游接口｜角色类型｜必要性｜可替代方案｜地域/时间｜材料状态`

分层原则：

- 先按功能和交易关系分层，再把已审核的公司、机构或用户角色放入节点；
- 同一公司纵向覆盖多个节点时分别登记，不因公司边界合并产业环节；
- 平台、双边市场、软件服务、内容行业或政府主导行业可使用并行链、网络或闭环，不强制画成单向直线；
- 代表性玩家只用于说明节点，不自动代表全部参与者或竞争格局。
- 当交付物、交易单位或商业系统发生明显变化时，建立双主链或多主链，再标出各链的汇合点和接口。例如产品制造链与资产运营链不能强行压成一条直线。

不要漏掉主产品之外的生产与交付依赖：制造业检查设备、耗材、工艺、检测与认证；服务业检查人力、软件工具、渠道与交付设施。只有确实影响当前任务的部分才展开，不能套同一张制造业清单。

为结构本身建立拓扑表，而不是只列节点：

`关系编号｜起始节点｜目标节点｜关系/接口类型｜流向｜主链/支链/反馈｜必要条件｜可绕行路径｜证据状态`

节点表回答“谁完成什么功能”，拓扑表回答“节点如何连接”；两者都不得用 Logo 排列或公司名单替代。

### 3. 按参与角色重画上下游关系

功能节点确定后，把每个重要节点展开为实际参与角色。角色链要回答：谁向谁采购，谁向谁交付，谁发起订单，谁付款和收款，谁承担结果责任。

先建立角色表：

`角色编号｜所在环节/任务｜角色名称｜上游角色及采购内容｜下游角色及交付内容｜付款与收款关系｜主要责任｜典型主体编号｜证据状态`

再建立角色关系表，使上下游关系可以被逐边核对和制图：

`关系编号｜上游角色｜下游角色｜交易或交付物｜订单发起者｜合同/合作关系｜付款者→收款者｜结算方式或账期｜数据/责任接口｜关系证据`

执行时注意：

- 角色是承担任务的一类参与者，企业是占据一个或多个角色的真实主体；不要把角色名和公司名混写；
- 同一角色可以连接多个上游或下游，同一企业纵向覆盖多个角色时分别登记；
- 只有公开材料明确支持时才写具名供应商或客户；只能确认客户类型时，就写客户类型，不推测企业名称；
- 交易关系、战略合作、参股关系和普通供货不是一回事，应分别标明。

具名企业之间的关系记录：`双方主体编号｜产品/服务｜关系类型｜阶段与发生时间｜来源位置`。送样、认证、合作意向、订单与批量供货分开；只能确认匿名客户或客户类型时，保留原披露。企业属于某环节，不代表它与图中所有上下游企业都有交易。

### 4. 识别核心环节并建立分层企业图谱

先根据本次研究目的判断哪些环节需要重点展开。可综合考察：对最终交付是否必要、替代难度、交易与客户控制力、技术或资本门槛、瓶颈传播范围、价值和责任集中度，以及正在发生的结构变化。不要用固定分数或统一层数机械判定。

按具体业务找企业：组合产品/技术/服务名与“生产、制造、集成、交付、运营”等角色动作；同时查年报、官网产品、项目与采购记录。行业分类不准时换业务词查，不只搜“龙头”。合并法人、品牌和集团内主体的重复记录，多业务企业可归入多个环节。

核对容易混淆的角色：设备生产者、使用者、经销商和维修商可能使用同一关键词；经营范围中出现“维修”不代表它只是维修商。专利支持技术线索，招投标需辨认采购/投标/中标角色，均不能直接替代实际经营证据；不同数据库转载同一原文也不是独立来源。

对每个纳入产业链的环节，列出能够确认的典型参与主体；核心环节更充分地覆盖头部、细分专家、成长企业及替代路线进入者，不凑固定数量。找不到资料时写明缺口。企业图谱记录：

`主体编号｜环节/角色｜企业或机构｜企业类型｜主要产品/能力｜已验证的上下游关系｜经营信号｜融资/上市状态｜代表性理由｜投资关注与风险｜证据状态`

企业类型可按课题使用“头部/专精型/成长型/早期进入者”等描述，但必须写明分类依据：

- 产品发布或融资只能证明进入该方向，不能自动证明已有客户、订单、收入、盈利或行业地位；
- “头部”或“代表性”应由产能、出货、收入、客户、项目、标准参与或其他可核实信号支持；
- “成长型”应尽量取得多期经营、客户、订单、产能利用或融资进展，不能只看宣传稿；
- 投资视角要同时列出已验证信号、可能催化剂、主要风险和仍缺证据；“潜在独角兽”只能作为带条件的观察项，不得写成事实或确定预测；
- 企业图谱用于说明产业角色和重点关注对象；需要完整份额排名、战略群组或竞争胜负时，另作竞争格局分析。

企业归属、经营阶段和投资受益分别判断：相关业务是否已形成产品、订单、收入，收入对该主体有多重要，行业变化通过什么机制使其受益或受损。行业热门不等于公司获益；涉及份额时注明地域、时间及数量/金额分母。

### 5. 建立四流矩阵

产品或服务的交付路径是结构底图；在此基础上逐节点核对四条流：

| 流 | 必答问题 |
|---|---|
| 订单流 | 谁提出需求、谁选型、谁签约、谁决定数量/规格、订单能否绕过中间层 |
| 资金流 | 谁付款、向谁结算、何时付款、是否预付/账期/抽成、谁占用营运资金 |
| 数据流 | 谁产生、采集、存储、访问、加工和复用数据；接口与权限由谁控制 |
| 责任流 | 谁承担交付、质量、售后、合规、安全、库存、违约和最终结果责任 |

数据流关注实际的数据、控制指令及访问权限；普通物流信息或研究者搜到的新闻，不另算产业数据流。未披露或与本题无关的路径直接注明，不为填表补造。

四流不要默认同向。重点标出：

- 付款者与使用者分离；
- 决策者、签约者和交付者分离；
- 数据控制者不直接收费；
- 利润获取者与责任承担者不一致；
- 订单经过一层，但资金或数据绕开该层。

必要时增加“每 100 元客户付款”的可复算情境表，只用于解释资金如何流转：

`节点｜收取金额｜代收/转付｜采购或分成｜税费口径｜暂留金额｜假设来源`

全部金额必须勾稽，且标为 `[情境]`。它不是行业平均利润率，也不能证明任何节点盈利；需要判断单体成本、利润和现金转换时，应另行取得相应经营数据。

### 6. 从系统变化寻找稀缺层

不要从热门公司反推“卡点”，按以下链条分析：

`需求或技术变化 → 原系统承受的压力 → 必须发生的能力变化 → 受约束的功能节点 → 可观察信号 → 绕行/替代路径 → 失效条件`

稀缺或瓶颈判断可检查：

- 合格供应者数量及其独立性，而非简单公司数量；
- 客户认证、监管许可、标准接入或验证周期；
- 扩产所需时间、资本、设备、良率爬坡、人才或材料纯度；
- 产能利用、交期、积压订单、配额、预订或库存变化；
- 专用设备、关键知识、数据、接口或基础设施控制；
- 客户切换成本、替代后的性能损失和重新认证成本；
- 一个节点中断后对全系统的影响范围与恢复时间。

瓶颈必须由至少一个机制和一个可观察信号支撑。供应商少不等于必然稀缺，毛利高不等于必然有权力；不设置通用的供应商数量、CR、毛利率或扩产周期阈值。

### 7. 判断权力、价值与责任是否错位

先把重点环节的三个问题分开，不能统称为“价值量”：

| 角度 | 怎么分析 |
|---|---|
| 成本构成 | 钱花在材料、设备、人力、能源、渠道还是售后；单耗、良率、利用率或交付效率怎样改变成本 |
| 利润获取 | 收费单位、价格、相关业务收入与利润怎样变化；谁能保留利润和现金，谁承担库存、回款及质保风险 |
| 瓶颈控制 | 谁控制难替代的能力或接口；扩张、切换、认证与恢复需要什么条件 |

有可比数据时量化，没有时解释机制并标明未知。成本占比高不等于利润高；代表企业毛利率不能简单平均成整个环节利润率，各层交易额也不能直接相加当作行业终端规模。第 5 节的 100 元表解释现金流转，不代替利润分析。

对每个关键节点询问：

- 谁定义规格、接口和准入条件；
- 谁掌握客户关系、流量入口或不可绕开的基础设施；
- 谁能延长对上游付款、要求下游预付或转移库存；
- 谁承担质量、合规、交付和售后责任；
- 谁能把成本上涨传导出去，谁只能自行吸收；
- 谁创造必要价值，谁实际保留收入或现金。

可使用多期、同口径经营信号辅助判断：

| 信号 | 可能说明 | 必须排除的替代解释 |
|---|---|---|
| 应付账款或付款周期上升 | 可能占用上游资金 | 采购增长、逾期付款或流动性恶化 |
| 合同负债/预收增加 | 可能获得客户预付 | 业务季节性、交付延期或退款义务 |
| 预付账款增加 | 可能受上游约束 | 主动锁价、扩产备货或并购影响 |
| 应收账款或回款周期上升 | 可能被下游占款 | 收入快速增长、客户结构或会计政策变化 |
| 毛利率与价格变化 | 可能反映价值获取变化 | 产品组合、原料价格、汇率和一次性因素 |

单一财务科目不能直接证明议价权；需要结合合同关系、供需状态、业务增长与多期变化解释。产业结构的重要性、单体盈利能力和竞争强弱不能互相替代。

研究涨价、扩产或技术冲击时，沿关系表追踪：`冲击｜先影响谁｜合同/技术传导方式｜谁吸收或转嫁｜时间滞后｜最终影响｜证据或情境假设`。不假设成本一定能等额传给下游。

### 8. 绘制替代路径与瓶颈迁移

对每个关键节点至少检查：

- **技术替代**：不同技术路线能否完成相同任务；
- **供应替代**：能否增加供应商、跨区域采购或国产/本地替代；
- **流程替代**：能否跳过该环节、改变接口或重新设计产品；
- **组织替代**：上下游能否纵向整合、自建或外包；
- **需求替代**：客户能否降低规格、延后采购或放弃使用。

每条替代路径记录：

`可行条件｜切换时间｜切换成本｜性能/质量损失｜重新认证要求｜新增责任｜受益/受损节点`

涉及技术代际时，用“旧路线的问题 → 新方案如何解决 → 新增代价 → 采用条件”解释变化，列出关键参数、良率/交付稳定性、认证和规模化进展。技术可行、客户接受和经济可行分开，不设通用良率或商用时间门槛。

技术授权、共同开发、分拆形成的能力来源，与技术相似、对标或替代分开记录；只有前者的对应证据才能支持技术来源连线。不同路线可长期共存，不强制画成单线淘汰史。

同时判断原瓶颈消失后，约束会不会迁移到设备、材料、人才、渠道、算力、能源、数据或合规等其他节点。

### 9. 比较结构版本，检查风险传播与缓冲

课题涉及已发生的结构变化、供应中断或韧性时，至少建立前后两个可追溯快照：

`结构事件｜前快照｜后快照｜新增/消失节点｜接口变化｜四流改道｜责任迁移｜瓶颈迁移｜缓冲点｜故障传播｜恢复路径｜证据状态｜失效条件`

执行时遵守：

- 前后快照必须使用可比的对象、地域、时间、粒度和拓扑边界；不可比时拆开陈述；
- 区分事件发生、结构生效和经营结果出现的时间，不把公告或规划当已完成重构；
- 沿节点与四流追踪故障影响，记录在哪个接口被放大、被吸收或转移，以及最终由谁承担责任；
- 缓冲点可以是库存、冗余供应、替代接口、保险或合同安排、产能余量、数据备份或监管兜底，但只有已审核材料支持时才纳入；
- 本 Skill 只解释已观察结构变化；未来阶段与扩散速度另列为待验证情境，不得把单次结构事件自动写成趋势。

### 10. 形成结构判断并设置反证

关键结论使用以下句式：

`[判断类型] 在[地域/时间/边界]内，[节点]因[约束机制]成为[瓶颈/稀缺层/关键接口]；证据表现为[信号]；但在[替代、扩产、需求变化或政策条件]下该判断会弱化或失效。`

结合本题保留适用的反证与缺口：

- 一个可能被高估的热门环节；
- 一个替代解释；
- 一个能让瓶颈判断降级的事实；
- 一个尚需补证的关键缺口。

对会改变结论的重要判断，附一行跟踪建议：`当前判断｜什么信号会改变它｜去哪里看｜何时复查`。关注项从具体结论推出，不凭空列热点。

### 11. 画出可编辑的产业链图

先从角色关系表画总览，说明谁向谁提供什么；长链按主链与关键分支分层排版。功能变化与角色关系确实不同、或存在双主链时，分图并标出接口；技术演进图按课题补充。

主图放关键角色和少量代表企业，完整企业名单放表格或分层卡片。美化只改变位置、配色、文字层级与连线路径，不增删研究确认的节点和关系。具体画法、模板及图源保存见 [产业链图绘制规范](references/产业链图绘制规范.md)。

## 验收

- [ ] 分层依据是必要功能和接口，不是公司名单或固定上中下游模板。
- [ ] 分析粒度和结构拓扑由决策用途决定，省略节点有理由，没有把全景/中景/近景变成固定层数。
- [ ] 节点表与拓扑表可以相互核对，主链、支链、反馈和绕行路径没有被 Logo 排列替代。
- [ ] 功能链、角色链和企业图谱已经分开表达；多条主链存在时没有被强行合并。
- [ ] 核心角色的上下游对象、交易/交付物、订单、付款和责任关系能够逐边核对。
- [ ] 核心环节已有代表性企业及入选依据；具名供应商、客户和合作关系有来源，企业标签没有越过经营证据。
- [ ] 涉及投资观察时，同时列出经营信号、资本状态、催化剂、风险和缺口，没有把“潜在独角兽”写成确定结论。
- [ ] 订单流、资金流、数据流和责任流均已覆盖，错位没有被省略。
- [ ] 瓶颈结论同时具备约束机制、可观察信号、替代路径和失效条件。
- [ ] 没有用固定 CR、供应商数量、毛利率或扩产周期阈值替代行业判断。
- [ ] 财务科目只作为需要解释的信号，没有单点推导议价权。
- [ ] 成本、利润与瓶颈分开判断；技术进展没有冒充批量供货或经营受益。
- [ ] “每 100 元客户付款”如被使用，已标为可复算情境而非行业均值或利润证明。
- [ ] 涉及结构变化时已区分前后快照、事件/生效/经营时间、四流改道、责任迁移、缓冲点与故障传播；未来趋势未被提前下结论。
- [ ] 外部输入只按确认口径使用，没有用本轮结构判断反向覆盖原始事实。
- [ ] 正常文件交付时，Mermaid 图源与美化图的节点、方向、关系标签一致，HTML 预览已离线打开检查；降级交付时，Markdown 与 Mermaid 图源结构一致；具名关系有证据。
- [ ] 补证任务和新材料状态清楚，没有把产业链判断扩写成无关竞争排名或交易建议。
